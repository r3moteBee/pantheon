# Client API: authentication, REST and the chat WebSocket

For building your own client (a desktop app in Electron, a mobile app, a script) against a Pantheon server. The web UI uses exactly these interfaces (`frontend/src/api/client.js`). The full REST reference is generated by FastAPI at `/docs` (Swagger UI) and `/openapi.json`; this page covers what you need to log in, chat and read results, and the rules a client has to follow.

All REST paths are under `/api`. The chat WebSocket is at `/ws/chat` (no `/api` prefix).

## Authentication

Pantheon is single-user. With `AUTH_PASSWORD` set, every `/api/*` and `/ws/*` request needs a session token; without it, auth is off (see [Auth disabled](#auth-disabled)).

| Step | Request | Result |
|---|---|---|
| Is a password needed? | `GET /api/auth/config` (public) | `{"auth_required": true}` |
| Log in | `POST /api/auth/login` `{"password": "..."}` | `{"token": "<session token>"}`, plus an HttpOnly `pantheon_session` cookie |
| Check a session | `GET /api/auth/session` | 200 `{"ok": true}`, or 401 |
| Log out | `POST /api/auth/logout` | revokes the token, clears the cookie |

- **Send the token** as `Authorization: Bearer <token>` (API clients) or the `pantheon_session` cookie (browsers). Tokens are never accepted in the query string.
- **Lifetime:** `AUTH_SESSION_DAYS` (default 30). Changing `AUTH_PASSWORD` invalidates every session.
- **Throttle:** 10 failed logins per client IP in 5 minutes → `429`.
- With auth off, `POST /api/auth/login` returns `{"token": "no-auth"}` for any password, so a client can use one code path.

Errors: `401 {"error": "Unauthorized"}` for a missing or expired token. A WebSocket that fails any check is refused during the handshake: the client sees the upgrade rejected with HTTP **403** (the server closes before accepting).

## Rules every client hits

**Origin.** Requests that change state (anything but GET/HEAD/OPTIONS) and every WebSocket handshake are checked against the `Origin` header (`api/auth.origin_is_allowed`):

- no `Origin` header → allowed (native HTTP/WebSocket libraries usually send none)
- same host as the server → allowed
- listed in `CORS_ORIGINS` → allowed (exact string match)
- anything else → `403 {"error": "Cross-origin request blocked"}` (WebSocket: handshake rejected with 403)

`CORS_ORIGINS` also drives browser CORS for REST (`allow_credentials=true`).

**Auth disabled.** With no `AUTH_PASSWORD`, the server only answers `Host` names that can't be DNS-rebound: IP addresses, single-label names (`localhost`), private suffixes (`.local`, `.lan`, `.home.arpa`, `.internal`, `.localhost`) and names listed in `ALLOWED_HOSTS`. Anything else gets `421` (WebSocket: handshake rejected with 403). Run Pantheon without a password only behind something that authenticates for it (a reverse proxy with SSO, a VPN).

**Insecure defaults.** While `VAULT_MASTER_KEY`, `SECRET_KEY` or `AUTH_PASSWORD` still have their public default values, only clients on the same machine are served. Everyone else gets `503` with the reason, and the WebSocket handshake is rejected (`ALLOW_INSECURE_DEFAULTS=true` overrides).

### Electron and mobile apps

- **WebSocket from a browser context.** The browser `WebSocket` API can't set an `Authorization` header, so it authenticates with the cookie, which is `SameSite=Strict` and only sent to the same site. Options:
  - Open the socket from Electron's **main process** (or a native library on mobile) with `Authorization: Bearer <token>`. These usually send no `Origin`, so the origin check passes.
  - Or add your app's exact `Origin` to `CORS_ORIGINS` and authenticate with the cookie. Check what Origin your build actually sends in devtools: `file://` pages, custom schemes and `http://localhost:<port>` dev servers all differ.
- **REST from a renderer** is cross-origin unless the page is loaded from the server, so its `Origin` must be in `CORS_ORIGINS`, and the Bearer header must be added by your fetch code.
- **Behind an SSO proxy** (for example oauth2-proxy in front of Pantheon with `AUTH_PASSWORD` empty), the proxy's sign-in decides access. An Electron app can complete that sign-in in a window and reuse its cookies. A native app needs a sign-in flow against the identity provider, or a separate authenticated route to Pantheon.

## Chat over the WebSocket

```
wss://<host>/ws/chat        (ws:// for plain http)
```

A connection carries one conversation turn at a time: the server reads the next client message only after the current turn has finished. Messages sent during a turn wait in order. Use one socket per conversation you want to run concurrently.

### Client → server

Every frame is a JSON object.

| Frame | Fields | Notes |
|---|---|---|
| message | `message` (string), `session_id` (string, optional), `project_id` (string, default `"default"`), `model_class` (optional) | Starts a turn. Omit `session_id` to start a new conversation: the server creates one and returns it in `session_start`. Reuse it for follow-ups; the history comes from the server, not from the client. |
| keepalive | `{"type": "ping"}` | Answered with `{"type": "pong"}`. The web UI pings every 15 s; proxies often close idle sockets. |
| accept a skill suggestion | `{"type": "skill_accept", "suggestion_id": "..."}` | Runs the paused turn with the suggested skill. |
| decline a skill suggestion | `{"type": "skill_decline", "suggestion_id": "..."}` | Runs the paused turn without it. |

Message conventions handled by the server:

- `/<skill-name> rest of message` runs that skill explicitly.
- `/model <agent|quick|code|long_context|vision|auto> [message]` pins the conversation to a model class (`auto` clears it). With no message, it only replies with the new setting. `model_class` in a message frame does the same as a field.
- **Attachments:**
  1. Upload with `POST /api/chat/attach` (multipart `file`, query `project_id`, optional `session_id`). It returns `{artifact_id, path, content_type, size, filename, indexing, extraction_job_id?}`; images are also queued for OCR / vision extraction.
  2. Reference the upload in the message text. Images: `[image: <path> (artifact:<artifact_id>)]` (models with vision receive the image itself). Other files: `<filename> (artifact:<artifact_id> — <path>)`.

### Server → client

Every event has a `type`. A normal turn: `session_start` → `model_route` → any number of `text_delta` / `tool_call` / `tool_result` → `done`.

| `type` | Fields | Meaning |
|---|---|---|
| `session_start` | `session_id` | The conversation this turn belongs to (new or reused). |
| `model_route` | `task_class`, `rule`, `reason`, `endpoint`, `model`, `est_tokens`, `notes` | Which model class answers this turn and why (router rule such as `fresh`, `quick`, `code`, `override`). |
| `model_pin` | `task_class` | Reply to `/model`: the conversation's pinned class (`auto` = none). |
| `skill_active` | `skill`, `description`, `auto?` | A skill is in use for this turn (`auto: true` when discovery picked it). |
| `skill_suggestion` | `skill`, `description`, `score`, `reason`, `suggestion_id` | Discovery mode "suggest": the turn is paused until the client sends `skill_accept` or `skill_decline`. |
| `text_delta` | `content` | Next piece of the reply. Concatenate in order. |
| `tool_call` | `id`, `name`, `args` | The agent called a tool. `name: "context_loaded"` is the server's own memory pre-load, not a model decision. |
| `tool_result` | `tool_id`, `name`, `result`, `is_error` | The tool's output (full text; the model sees a capped copy). |
| `done` | `full_response`, `iterations`, `truncated`, `route` | The turn finished. `full_response` is the reply exactly as saved in the conversation; use it as the final text. `truncated: true` means the agent hit its tool-iteration cap. `route` is the routing record (the `model_route` fields plus the served model and `decision_id`) when routing ran. |
| `error` | `message`, `status?` | The turn (or the frame) failed: invalid JSON, empty message, an expired suggestion, or a model/provider error. |
| `pong` | | Keepalive reply. |

Replies are Markdown. Tool results may contain `[DISPLAY:artifact://<id>]` (e.g. images from `generate_image`) or `[DISPLAY:workspace://<path>]` markers; the web UI renders them as inline previews (`frontend/src/components/chat/ToolCallBlock.jsx`). Fetch the content with `GET /api/artifacts/{id}/raw` or `GET /api/files/read?path=...&project_id=...`.

**Disconnects.** If the socket drops mid-turn, the server finishes the turn and saves the reply anyway. Reconnect and load it with `GET /api/conversations/{session_id}`.

### Minimal example (Node, `ws` package)

```js
import WebSocket from 'ws'

const base = 'https://pantheon.example'
const { token } = await (await fetch(`${base}/api/auth/login`, {
  method: 'POST', headers: { 'content-type': 'application/json' },
  body: JSON.stringify({ password: process.env.PANTHEON_PASSWORD }),
})).json()

const ws = new WebSocket(base.replace(/^http/, 'ws') + '/ws/chat',
  { headers: { Authorization: `Bearer ${token}` } })   // no Origin header is sent
let sessionId
ws.on('open', () => ws.send(JSON.stringify({ message: 'What is on my plate this week?', project_id: 'default' })))
ws.on('message', (raw) => {
  const e = JSON.parse(raw)
  if (e.type === 'session_start') sessionId = e.session_id          // reuse for follow-ups
  if (e.type === 'text_delta') process.stdout.write(e.content)
  if (e.type === 'done') { console.log('\n---\n' + e.full_response); ws.close() }
  if (e.type === 'error') { console.error(e.message); ws.close() }
})
```

## Chat without a socket

`POST /api/chat` `{"message", "session_id"?, "project_id"?}` runs a whole turn and returns `{"session_id", "response", "project_id", "route"}` when it is done. There is no streaming and no `tool_call` events; skill suggestions are applied automatically (no chip to accept). This suits scripts and bots.

## Reading conversations and projects

| What | Request |
|---|---|
| Projects | `GET /api/projects` → `{projects: [{id, name, description, ...}], count}` |
| Conversations in a project | `GET /api/conversations?project_id=...&limit=50` |
| One conversation's messages | `GET /api/conversations/{session_id}?limit=500` → `{messages: [{role, content, timestamp, metadata}], project_id, metadata}` |
| Delete a conversation | `DELETE /api/conversations/{session_id}` |
| Artifacts | `GET /api/artifacts?project_id=...` (see [artifacts-feed.md](artifacts-feed.md)); content via `GET /api/artifacts/{id}/raw` |
| Background jobs | `GET /api/jobs?project_id=...`, `GET /api/jobs/{id}` (tasks the agent started, with progress) |
| Server status | `GET /api/health` (public) → `{"status": "ok", "version": "..."}` |

Everything else (memory, skills, connections, settings, export/import) is in `/docs`.
